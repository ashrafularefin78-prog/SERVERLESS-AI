# Interface languages

The app offers coding help for 66 languages while its own interface was English
only. That line is now drawn differently: **the chrome is translated, the content is
not.**

## What is translated

Navigation, controls, section headings, dialog titles, buttons, placeholders, and
`aria-label`s — the strings in `index.html` marked with `data-i18n`,
`data-i18n-aria-label`, or `data-i18n-placeholder`. A handful of strings the app
sets from code (the composer placeholder, the model button's three states, the
language row) go through `t()`.

Shipped locales: **English, Spanish, German**. A browser set to something else falls
back to English rather than showing a half-translated mix.

## What is deliberately not translated

| Surface                                                            | Why                                                                                                     |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| Model descriptions, licence text, and the model catalogue          | Written by publishers; paraphrasing them would misquote a licence                                       |
| Toasts, confirm dialogs, and diagnostic messages from `src/app.ts` | Still English, and the honest label for a gap is a gap, not a machine translation of a security warning |
| The built-in assistant's replies                                   | It answers in the language you write in, which is a runtime behaviour, not a string table               |
| Documentation in `docs/`, `README.md`, `SECURITY.md`               | Maintained in one language so the security claims stay auditable                                        |

If you want a surface moved from the second row to the first, the work is: wrap the
string in `t("English text")`, add it to `src/locales/<code>.ts`, and add the key to
the `runtime` set in `tests/unit/i18n.test.js` (that set exists so an unused key
fails the build).

## How it works

- **English is the key.** `data-i18n="Settings"` holds the English text and the
  English text _is_ the key, so a missing translation renders English and switching
  back to English restores the markup exactly — no second English catalog, no
  "Settings" placeholder keys, no drift between key and copy.
- **Locales are separate chunks.** `src/i18n.ts` maps a code to a dynamic import;
  Vite splits `src/locales/es.ts` and `de.ts` into their own files, so a user who
  stays on English downloads nothing extra. The interface core costs ~1.7 kB gzip.
- **`system` follows the browser.** `resolveLocale(preference, navigator.languages)`
  matches on the base tag (`es-MX` → `es`), falls back to English, and is unit-tested
  for a French-only browser, an empty list, and an unknown saved value.
- **Attributes are translated too.** A screen reader announces `aria-label` as
  loudly as visible text, so `applyStaticTranslations` handles both in one pass and
  sets `lang` on the translated elements.

## Adding a language

1. Add the code to `LOCALES` in `src/i18n.ts` and to `Settings["language"]` in
   `src/types.ts`.
2. Copy `src/locales/es.ts`, translate the values, and leave any key you are unsure
   about out — it will fall back to English.
3. Add the import to the `CATALOGS` map. The unit test will tell you which keys the
   markup expects and which ones you have invented.

## Testing

- `tests/unit/i18n.test.js` — locale resolution, fallback, and three catalog checks:
  every marked key is translated, no catalog entry is unused, and no value is an
  accidental copy of the English string.
- `tests/e2e/i18n.spec.js` — a Spanish browser gets Spanish chrome without touching
  Settings, a German browser still gets an English reply to an English prompt, an
  unsupported browser language falls back, and switching back to English restores
  the markup.
