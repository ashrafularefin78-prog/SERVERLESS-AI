# Security notes and threat model

LocalMind is a static browser app. There is no backend to breach and no prompt data is sent to a server. That removes a large class of risk, but it does not make the app automatically safe. This document describes what is protected, what is not, and how to reduce risk.

This is a small project, not an audited product.

## Assets

- Conversation text, custom instructions, memory notes, and settings stored in IndexedDB.
- Downloaded model weights and runtime files in browser caches.
- The origin's integrity: a script injection could read chats, make requests, or alter the UI.
- User trust in the "100% local" claim.

## Trust boundaries

1. **The page and its bundled code.** Pinned npm dependencies are bundled at build time. There are no third-party scripts at runtime.
2. **Model output.** Untrusted text generated by a statistical model. It can contain markup, misleading claims, links, or attempts to imitate the UI.
3. **Downloaded model files.** Weights and WebLLM WASM kernels come from Hugging Face and GitHub raw at runtime. They are not authored by this project.
4. **Other browser extensions and local malware.** Outside the app's control. An extension with page access can read everything.
5. **The static host.** A compromised host or DNS can serve modified JavaScript. HTTPS and host security are required.

## Threats and mitigations

### XSS through model output

**Threat:** The model emits `<img onerror=...>`, a `javascript:` link, or an event handler that runs in the page and reads chats or sends them elsewhere.

**Mitigation:**
- Output is parsed with marked, then sanitized with DOMPurify.
- Dangerous tags are forbidden (script, iframe, object, embed, form controls, media, SVG, MathML, template, style, link, meta).
- `style`, `srcset`, and `formaction` attributes are forbidden.
- Links are rewritten to `target="_blank"` with `rel="noopener noreferrer"`; links with schemes other than `http(s)` and `mailto` are replaced with plain text.
- Images are not rendered, so image-based tracking and `onerror` payloads do not run.
- Streaming text is inserted with `textContent`; markdown parsing happens only after the reply finishes.
- A CSP forbids inline scripts, eval (except WebAssembly compilation), and non-self scripts.

**Residual risk:** Sanitizer bypasses are possible. Keep DOMPurify updated; do not add raw HTML rendering paths.

### Prompt injection

**Threat:** Text in a prompt or future document tells the model to ignore instructions, reveal context, or produce dangerous output.

**Mitigation:** The app has no tools, no browsing, no file access, and no automatic actions, so a successful injection can only produce text. System prompts tell the model it cannot browse or access files.

**Residual risk:** If RAG or tools are added, treat retrieved text and tool output as untrusted. Require explicit user confirmation before any side effect.

### Malicious or poisoned model files

**Threat:** A tampered weight file or WASM kernel causes memory corruption, exfiltrates data, or produces harmful output.

**Mitigation:** Models come from well-known Hugging Face repositories; WebLLM kernels come from the official MLC GitHub organization. The app does not accept user-uploaded models or arbitrary URLs. Browsers sandbox WASM execution.

**Residual risk:** The app does not independently verify file hashes. WebLLM may verify its own artifacts where metadata is available, but this is not a substitute for a full supply-chain review. If you need stronger guarantees, host reviewed artifacts yourself and pin hashes.

### Data at rest

**Threat:** Another user of the device, a browser profile compromise, or a malicious extension reads chats.

**Mitigation:** Data is confined to IndexedDB and browser caches for this origin. "Clear all data" deletes conversations, settings, caches, service worker registrations, and local/session storage.

**Residual risk:** Data is not encrypted at rest. Anyone with access to the browser profile can read it. Use a separate OS account or profile for sensitive work. Do not enter secrets.

### Supply chain

**Threat:** A compromised npm package injects code at build time or runtime.

**Mitigation:**
- `package.json` pins exact versions; `package-lock.json` records the full tree.
- Production dependencies are small: WebLLM, wllama, marked, DOMPurify.
- No CDN scripts, no analytics, no remote fonts.
- The build injects a CSP and the app ships a service worker only in production.
- Review lockfile diffs before updating.

**Residual risk:** A compromised maintainer or build machine can still ship bad code. Rebuild from a clean checkout for releases.

### Service worker and cache poisoning

**Threat:** A stale or malicious service worker serves modified app code.

**Mitigation:** The worker is same-origin, versioned per build, caches only same-origin responses, never intercepts cross-origin model traffic, and ignores non-GET requests. A new build changes the cache name and deletes old caches.

**Residual risk:** A compromised origin can always serve a malicious worker. HTTPS and host account security are essential.

### Clipboard and links

- Copy uses the async Clipboard API with a `document.execCommand("copy")` fallback. Only user-triggered actions copy data.
- External links open with `rel="noopener noreferrer"` in a new tab.
- `form-action 'none'` prevents accidental form submission if a future template introduces a form.

### Network metadata

Even though prompts stay local, the first model download reveals your IP address to Hugging Face and GitHub, along with which model you chose. After caching, normal chats make no requests. A host, ISP, or proxy can still see the app files you load.

## What the app deliberately does not do

- No remote inference, API keys, or account system.
- No telemetry, analytics, crash reporting, or remote logging.
- No user-uploaded models, arbitrary model URLs, plugins, or tool execution.
- No automatic network access during a chat after the model is loaded.
- No raw HTML rendering of model output.

## Hardening checklist for deployment

- Serve over HTTPS only.
- Add security headers at the host if possible:
  - `Content-Security-Policy` (the build ships a meta tag; headers are stronger)
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: no-referrer`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
  - `Cross-Origin-Opener-Policy: same-origin`
- Keep `frame-ancestors 'none'` in the header CSP. It is intentionally absent from the meta tag because browsers ignore it there.
- Pin dependency versions and review upgrades.
- Re-run the XSS and privacy checks in [TEST_PROMPTS.md](TEST_PROMPTS.md) after changes.
- Publish releases from a clean build and keep the lockfile in version control.

## Reporting

If you find a vulnerability, open a private security advisory on the repository rather than a public issue with exploit details.
